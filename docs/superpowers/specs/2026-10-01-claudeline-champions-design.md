# Claudeline Champions: design and roadmap

Date: 2026-10-01
Status: approved design, pre-implementation
Owner: Thomas Mueller (sv-tmueller)

## 1. Intent

Claudeline Champions is an original top-down arena brawler in the spirit of
Bloodline Champions: WASD movement, mouse-aimed skillshots, no auto-targeting,
cooldown-based kits with an energy-fuelled ultimate, short best-of rounds in
small symmetric arenas.

Goals, in order:

1. A playable local 2v2 against bots in the browser (the "first playable").
2. 3v3, more champions, more arenas, polish.
3. Online multiplayer with a casual queue and a ranked ladder.
4. A Steam release of the same game through an Electron shell.

This is a long-running passion project built mostly by AI agents under human
direction. There is no deadline. Every design choice below favours
reproducibility, testability and a tight agent feedback loop over anything an
editor-driven workflow would offer.

Success for the first playable: `npm run dev`, open the browser, pick a
champion, play a best-of-five 2v2 (one human plus one bot against two bots)
on arena 1 at a steady 60 fps on the dev machine, and have it feel responsive.

## 2. Decisions

| ID | Decision | Alternatives rejected |
|----|----------|-----------------------|
| ADR-001 | TypeScript everywhere: Three.js client, Node server, Electron shell later. npm workspaces, no extra package manager. | Godot 4 with web export (web is its weakest target, agents fight the scene and import pipeline). Bevy (no toolchain, weaker UI, moving API). Unity (licensing, editor-centric). |
| ADR-002 | Server-authoritative simulation on a fixed tick. One pure TypeScript sim package runs identically in the browser, in tests, in bots and on the server. | Deterministic lockstep (needs bit-exact cross-machine floats and input delay, easier to cheat). Client-authoritative (unfixable later). |
| ADR-003 | Abilities are typed TypeScript modules composed from a small effects toolkit. | JSON ability language plus interpreter (a DSL to maintain for a single authoring team). |
| ADR-004 | Assets are generated by Blender Python scripts run headless from the repo. Arena visuals are generated from the same JSON the sim uses for collision. Generated models are committed. | Hand modelling in the Blender UI (not reproducible by agents). Allowed later for an art pass, script-first remains the rule. |
| ADR-005 | Original content only: original champion names and kits inspired by the archetypes, original arena layouts, no Stunlock names, art or text. | Copying the original roster. |

Amended 2026-10-17 by [batch #134 decision 1](https://github.com/sv-tmueller/claudeline-champions/issues/134#issuecomment-6232034441): ADR-006 (the first online cut) is recorded in [ADR-006](../../architecture/decisions/ADR-006-online-first-cut.md).

## 3. Architecture

### 3.1 Repository layout

```
package.json                npm workspaces root, scripts: dev, check, test, lint, typecheck, e2e
packages/sim/               pure TypeScript, zero runtime deps, no DOM types
packages/bots/              depends on sim only
packages/client/            Vite + Three.js, depends on sim and bots
packages/server/            Node authoritative match server (milestone 6)
packages/protocol/          shared network message types (milestone 6)
packages/desktop/           Electron shell + Steamworks (milestone 8)
tools/blender/              Python scripts run via Blender in background mode
data/arenas/                arena definitions (JSON), read by sim and by Blender scripts
data/kits/                  roster kit definitions (JSON), read like arenas
assets/models/              generated .glb files, committed
docs/architecture/          living reference for humans and agents
docs/design/                game design documents (rules, roster, arenas)
docs/roadmap.md             living roadmap
docs/superpowers/specs/     approved designs (this file)
.github/workflows/ci.yml    runs `npm run check` on every pull request
```

Amended 2026-10-05 by [batch #53 decision 1](https://github.com/sv-tmueller/claudeline-champions/issues/53#issuecomment-5954741436): `data/kits/<id>.json`
holds the roster kits as plain data (`KitDef`), checked by `validateKit` and read the way arenas are.

### 3.2 Dependency rules

- `sim` imports nothing outside itself. Its tsconfig has no DOM lib. It never
  reads the wall clock, never calls `Math.random`, never touches `window`,
  `document`, `fetch` or Node built-ins.
- `bots` imports `sim` only.
- `client` imports `sim` and `bots`. It owns all rendering, input, audio and UI.
- `server` imports `sim`, `bots` and `protocol`. It never imports `client`.
- Lint enforces these boundaries. A violation fails `npm run check`.

Amended 2026-10-17 by [batch #134 decision 1](https://github.com/sv-tmueller/claudeline-champions/issues/134#issuecomment-6232034441), for milestone 6 (the full text is [section 3 of the online design](2026-10-17-online-design.md#3-package-layout-and-rules)):

- `protocol` holds the message types, `PROTOCOL_VERSION` and pure JSON encode
  and decode with validation. It has no I/O, no transport and no game logic.
  It imports relative paths and `@claudeline/sim` only. It has the host bans
  of `sim`: the globals `Date`, `performance`, `setTimeout`, `setInterval`,
  `window`, `document` and `fetch`, the properties `Math.random`, `Date.now`
  and `performance.now`, no Node built-ins, and no dynamic `import()` or
  `import()` types. It does not have sim's math ban. Its tsconfig has
  `lib: ["ES2023"]`, `types: []` and `erasableSyntaxOnly`.
- `server` imports `sim`, `bots`, `protocol`, `ws` and `node:` built-ins, with
  Node globals. It never imports `client`, and it may read the wall clock.
- `client` imports `sim`, `bots` and `protocol`, replacing "`client` imports
  `sim` and `bots`" above. It never imports `server`, and a lint deny rule
  names that, for static and dynamic imports: the client has no import rule
  today.
- `sim` and `bots` are unchanged.

### 3.3 Data flow

```
keyboard+mouse -> client input mapper -> PlayerInput (per tick)
bots            -> bot.think(state)   -> PlayerInput (per tick)
PlayerInput[] + GameState -> sim.step() -> GameState' + events[]
GameState' -> client renderer (interpolated) + HUD
GameState' -> server snapshot -> remote clients          (milestone 6)
```

Locally the client, the bots and the sim live in one process, so there is zero
input latency. Online, the same sim runs on the server and clients send their
PlayerInput stream.

## 4. Simulation core (`packages/sim`)

### 4.1 Time and space

- Fixed tick rate: 60 Hz. `TICK_RATE = 60`, `DT = 1 / 60`. All durations in
  the sim are integer tick counts, never seconds.
- 2D plane in meters. Sim coordinates `(x, y)`. `+x` is east, `+y` is north.
  The client maps sim `(x, y)` to Three.js `(x, 0, -y)` so screen-up is `+y`.
- Champions are circles of radius 0.5 m. Obstacles are circles or axis-aligned
  rectangles. The arena boundary rectangle is a wall.
- Line of sight is a segment-versus-obstacle test against obstacles flagged
  `blocksProjectiles`.

### 4.2 Input record

One `PlayerInput` per player per tick:

```ts
interface PlayerInput {
  moveX: -1 | 0 | 1;      // screen-relative WASD
  moveY: -1 | 0 | 1;
  aimX: number;            // world position in centimeters, integer
  aimY: number;
  buttons: number;         // bitmask: M1, M2, SPACE, Q, E, R, F, SHIFT
}
```

Aim is quantized to integer centimeters so the record is small and stable on
the wire later. A missing input for a player on a tick is treated as "no
movement, no buttons, aim unchanged".

### 4.3 State

`GameState` is plain, JSON-serializable data: no classes with methods, no
`Map`, no `Set`, no closures. Entities live in arrays ordered by ascending id.
Iteration order is always id order. This gives:

- `createMatch(config: MatchConfig, arena: ArenaDef, seed: number, kits: readonly KitDef[] = []): GameState`. Amended 2026-10-05 by [batch #47 decision 1](https://github.com/sv-tmueller/claudeline-champions/issues/47#issuecomment-5950051780): the optional `kits` argument (#43) extends the three-argument form compatibly, and with no kits no champion has abilities. A `config` without `roundsToWin` starts free play, with no rounds (#54; see `docs/architecture/simulation.md`).
- `step(state: GameState, inputs: PlayerInput[]): void` advances one tick in place
- `cloneState(state): GameState`
- `checksum(state): number` for replay and desync tests
- `state.events: SimEvent[]` cleared at the start of each tick, appended during
  the tick: ability cast, projectile spawn, hit, heal, status applied, death,
  round start, round end, match end. The renderer and audio consume events.
  Events are not needed to reproduce state.

Randomness goes through a seeded PRNG stored in the state. Given the same seed
and the same input stream, `checksum` after N ticks is identical on every run.

### 4.4 Entities

- Champion: team, champion id, position, velocity, facing (aim angle), health,
  max health, energy 0..100, per-slot cooldowns in ticks, cast state (slot,
  remaining windup ticks), statuses, alive flag.
- Projectile: owner, position, velocity, radius, remaining lifetime ticks,
  pierce flag, on-hit effect reference.
- Area: owner, shape (circle or cone or rectangle), position, remaining ticks,
  tick interval, effect reference.
- Obstacle: static, from the arena definition.
- Ring (sudden death): center, current radius, damage per second.

### 4.5 Statuses

Catalog: stun, root, silence, slow (percent), haste (percent), shield
(absorb amount), damage over time, heal over time, knockback (velocity impulse
decaying over ticks), invulnerable. Each status has a remaining tick count. The
same status from the same source refreshes duration rather than stacking.
Different sources stack unless the design doc says otherwise for that status.
Stun blocks movement and casting. Root blocks movement only. Silence blocks
casting only.

Amended 2026-10-27 by [batch #193 decision 2](https://github.com/sv-tmueller/claudeline-champions/issues/193#issuecomment-6434714202), for #158, per the roster v3 design section 4.1 (#175): the catalog gains `wound`, whose stacks add from every source, the same one included, so the same-source refresh rule does not apply to it.

### 4.6 Abilities

Slots follow the Bloodline layout: `M1` (basic), `M2` (secondary), `SPACE`
(mobility), `Q`, `E`, `R` (utility, offense, defense), `F` (ultimate). Holding
`SHIFT` with a slot casts that slot's EX variant where the kit defines one.
Each kit defines exactly two EX variants.

- EX variants cost 25 energy. The ultimate costs 100 energy. Energy is earned
  only by landing abilities on enemies and, for support kits, by healing
  allies. Energy resets to 0 at the start of each round.
  Amended 2026-10-31 by [#218](https://github.com/sv-tmueller/claudeline-champions/issues/218):
  energy also comes from the energy orb, one contested pickup per round (rules.md section 3.3);
  the orb is an arena source, and kits add no other.
- Every ability has: cooldown ticks, windup ticks (0 for instant), movement
  rule during windup (free, slowed, locked), and a list of effects.
- Effects toolkit (the only primitives kits may use): `projectile`, `dash`,
  `meleeArc`, `area`, `applyStatus`, `heal`, `shield`, `teleport`,
  `knockback`, `energyGain`. New primitives are added to the toolkit through
  the design doc first, then the sim.
- No global cooldown. Casting is blocked while another windup is in progress,
  while stunned, and while silenced (mobility slot included).
- Health does not regenerate during a round except through healing effects.

### 4.7 Match flow

State machine: `warmup -> round -> roundEnd -> (round | matchEnd)`.

- Warmup: 3 seconds, movement and casting locked, champions at spawn.
- Round: 90 seconds. A team wins the round when every enemy champion is dead.
- Sudden death: when the round timer expires, a ring centred on the arena
  shrinks linearly from `ring.startRadius` to `ring.endRadius` over 30 seconds
  and deals `ring.damagePerSecond` to champions outside it, then holds at
  `endRadius` until the round resolves.
- If both teams lose their last champion on the same tick the round is a draw:
  no score, next round.
- Round end: 3 seconds, then full heal, cooldown reset, energy to 0, respawn at
  the team's spawn points.
- Match end: first team to `roundsToWin` (default 3) round wins.
- `MatchConfig`: team size (2 or 3), per-player champion id and team, rounds to
  win. The parsed arena and the seed are `createMatch` parameters.
  Amended 2026-10-05 by [batch #53 decision 3](https://github.com/sv-tmueller/claudeline-champions/issues/53#issuecomment-5954853203): rounds to win is the optional
  `MatchConfig.roundsToWin`; a config without it is free play, with no warmup, round clock, ring or
  round end, and the standard match passes `DEFAULT_ROUNDS_TO_WIN = 3`.
  Amended 2026-10-31 by [#218](https://github.com/sv-tmueller/claudeline-champions/issues/218): the
  optional `MatchConfig.energyOrb`, an orb point `{ x, y }`, turns the energy orb on; a config
  without it has no orb. The points live in `data/orbs.json`, and the callers read them with
  `orbPointFor`.

### 4.8 Determinism rules (enforced by review and tests)

1. No `Date`, `performance.now`, timers, `Math.random`, or I/O in `sim`.
2. All time is integer ticks. All durations in config are converted to ticks
   once, at `createMatch`.
3. Iterate arrays in index order; never iterate object keys for gameplay logic.
4. The sim uses only correctly rounded operations (`+`, `-`, `*`, `/` and
   `Math.sqrt`), the exact helpers `Math.abs`, `Math.round`, `Math.min`,
   `Math.max` and `Math.imul`, the constant `Math.PI`, and the deterministic
   fdlibm ports in `packages/sim/src/dmath.ts`: `atan`, `atan2`, and `sin` and
   `cos` for |x| below 1647099 (just under 2^20 · π/2). V8's transcendental
   `Math` functions and the `**` operator are not correctly rounded and can
   differ in the last bit between CPU architectures, so lint bans them in sim
   source. Kits prefer constant sines and cosines in their data over runtime
   calls. Guard against `NaN`: tests assert `checksum` is finite and that no
   position or health is `NaN`. Amended 2026-10-02 by
   [batch #23 decision 9](https://github.com/sv-tmueller/claudeline-champions/issues/23#issuecomment-5943538722),
   replacing "Floats are fine (same engine everywhere)": the same V8 version
   gives different last bits for `Math.atan2`, `Math.sin` and `Math.cos` on
   x86 Linux and ARM macOS.
5. Recorded input replays with expected checksums are committed as fixtures.
   Changing gameplay intentionally means regenerating the fixture in the same
   change.

## 5. Client (`packages/client`)

- Loop: fixed-step accumulator. The sim steps at 60 Hz, rendering runs at the
  display rate and interpolates positions between the last two ticks. Rendering
  never steps the sim.
- Input: keyboard and mouse map to a `PlayerInput` each tick. Mouse aim is a
  ray from the camera to the ground plane, quantized to centimeters.
- Camera: fixed, tilted about 55 degrees from horizontal, positioned so the
  whole arena fits the viewport with margin. No rotation, no zoom in v1.
- Scene: arena model and champion models loaded from glTF under
  `assets/models/`. Projectiles and areas are simple meshes. Effects start as
  meshes and billboards. Animations come from glTF clips once rigs exist.
- HUD: an HTML and CSS overlay. Health and energy bars, cooldown icons per
  slot, round score, round timer, ring warning, kill feed. A debug overlay
  draws collision circles, obstacles, projectiles and line of sight.
- Platform interface (Steam readiness): `Platform { identity(), loadSettings(),
  saveSettings(), unlockAchievement(id), openUrl(url) }`. `BrowserPlatform` is
  the only implementation until milestone 8. Game code only talks to the
  interface.
  Amended 2026-10-16 by [batch #105 decision 4](https://github.com/sv-tmueller/claudeline-champions/issues/105#issuecomment-6140641300):
  `Platform` also has a `sound` sub-object (`SoundOutput { unlock(),
  setMuted(on), play(sound) }`), so a desktop build can swap the sound, and
  `Settings` carries the mute.
- Assets load relative to the app base path, never from absolute URLs.
- Rendering scales from a browser tab to a fullscreen 4K desktop window:
  resolution-independent camera framing, device-pixel-ratio aware canvas.

## 6. Bots (`packages/bots`)

- API: `createBot(playerId, difficulty, seed) -> { think(state: GameState): PlayerInput }`.
  Bots run inside the same process as the sim (browser locally, server online).
  They read the full state; fairness comes from difficulty tiers, not hidden
  information.
- Navigation: A-star over a coarse grid (0.5 m cells) baked from the arena
  definition, plus local steering to avoid champions and projectiles.
- Decisions: utility scoring over candidate intents: engage, kite, dodge a
  predicted projectile, retreat, peel for an ally, hold position, use the
  ultimate. Each champion kit ships a small bot profile describing preferred
  range and which slots are openers, escapes and finishers.
  Amended 2026-10-05 by [batch #53 decision 2](https://github.com/sv-tmueller/claudeline-champions/issues/53#issuecomment-5954808062): the kit does not ship the bot
  profile. Bots derive the preferred range from the kit and keep their profiles in `packages/bots`;
  openers, escapes and finishers are not built.
  Amended 2026-10-06 by [#81](https://github.com/sv-tmueller/claudeline-champions/issues/81) (batch #80): openers and escapes are built as stateless slot conditions in the bots' profiles
  (bots.md, Openers and escapes); the one finisher is bots.md's Finisher rule; per-slot finishers are not built.
  Amended 2026-10-17 by [batch #134 decision 3](https://github.com/sv-tmueller/claudeline-champions/issues/134#issuecomment-6232087847):
  dodging a predicted projectile is a movement override of the acted intent,
  decided on the current state after the aim, and not a scored intent through
  the reaction delay (bots.md, Dodge). The reaction is the tier's cast delay,
  one coin is drawn per projectile, and the dodge probabilities are 0.25, 0.5
  and 0.75.
- Aim: lead moving targets using their current velocity; add a tier-dependent
  angular error.
- Difficulty tiers: easy, normal, hard. They differ in reaction delay (ticks
  between a change in the world and a change in intent), aim error, and
  dodge probability.
- Bot-versus-bot headless matches are integration tests: a full match must
  finish, invariants must hold, and no `NaN` may appear.

## 7. Online and ladder (principles only, implemented from milestone 6)

- Each match runs in its own server process on the same sim at 60 Hz. Clients
  send `PlayerInput` with a tick number. The server sends snapshots at 20 Hz,
  full at first, deltas later. Clients render opponents about 100 ms behind
  and interpolate. Client-side prediction and reconciliation for the local
  champion come after interpolation works.
- `protocol` holds message types only. `sim` knows nothing about networking.
- A separate matchmaking service owns accounts, queues and ratings. Casual and
  ranked queues share one matchmaker. Only ranked updates the visible Glicko-2
  rating; casual uses a hidden rating for fairness.
- Server authority is the anti-cheat baseline. No client-trusted state.

Amended 2026-10-17 by [batch #134 decision 1](https://github.com/sv-tmueller/claudeline-champions/issues/134#issuecomment-6232034441): the first online cut is designed in [the online design](2026-10-17-online-design.md). A router process owns the one port and forks one process per room, so each match still runs in its own process. `protocol` holds a pure codec as well as the message types (see section 3.2). Online play never pauses.

## 8. Asset pipeline (`tools/blender`)

- Blender runs locally in background mode: `tools/blender/run.sh <script.py> -- <args>`
  locates Blender at `$BLENDER` or `/Applications/Blender.app/Contents/MacOS/Blender`.
- `gen_arena.py --arena data/arenas/<id>.json --out assets/models/arenas/<id>.glb`
  builds floor, boundary walls and every obstacle from the arena definition.
  Node names: `Floor`, `Wall_N`, `Wall_S`, `Wall_E`, `Wall_W`,
  `Obstacle_<index>` matching the obstacle's index in the JSON.
- `gen_champion.py --champion <id> --out assets/models/champions/<id>.glb`
  builds a low-poly placeholder humanoid. Rigs and animation clips (`Idle`,
  `Run`, `Attack`, `Cast`, `Hit`, `Death`) are added in milestone 5.
- `validate_glb.py` uses only the Python standard library: checks the glb
  magic and chunk layout, and that required node names are present. CI runs it
  on committed assets so Blender itself is never needed in CI.
- Generated `.glb` files are committed. Regenerating is a local step.

### 8.1 Arena definition (`data/arenas/<id>.json`)

```json
{
  "id": "arena01",
  "name": "Arena 1",
  "size": { "width": 30, "height": 20 },
  "spawns": {
    "teamA": [[-12, 2], [-12, -2], [-12, 0]],
    "teamB": [[12, 2], [12, -2], [12, 0]]
  },
  "obstacles": [
    { "type": "circle", "x": 0, "y": 0, "r": 1.5, "height": 2.0, "blocksProjectiles": true },
    { "type": "rect", "x": -6, "y": 5, "w": 3, "h": 1, "height": 0.6, "blocksProjectiles": false }
  ],
  "ring": { "startRadius": 18, "endRadius": 3, "damagePerSecond": 10 }
}
```

- `size` is the playable rectangle centred on the origin, in meters.
- `spawns` lists up to three points per team; a 2v2 uses the first two.
- Every obstacle blocks movement. `blocksProjectiles` also blocks line of sight.
- `height` is visual only.
- Arena 1 is left-right symmetric (mirror across `x = 0`).

## 9. Testing and quality gates

- `npm run check` runs lint, typecheck, unit tests and the Playwright smoke
  test. It is the check suite every package must pass. CI runs it on every
  pull request.
- Unit tests (Vitest): sim math, collision, statuses, abilities, match flow,
  replay fixtures with checksums.
- Integration tests: bot-versus-bot headless matches.
- Smoke tests (Playwright): the client loads, renders a frame, and a screenshot
  is written to the test output for human review.
- Asset validation: `validate_glb.py` over `assets/models/`.
- Strict TypeScript, ESLint with the dependency-boundary rule.

## 11. Roadmap

Each milestone is several batches of up to six independent packages. Package
lists are candidates, sliced batch by batch at dispatch time.

1. **Foundations** (batch 1). Monorepo scaffold with the check suite and CI.
   Architecture reference docs and the living roadmap. Game rules and controls
   doc. Roster v1 doc. Blender pipeline bootstrap with arena 1 definition and
   placeholder models.
2. **Walking in the arena.** Sim: champion entity, movement, obstacle and
   boundary collision, arena loading from JSON, replay fixtures. Client: scene
   bootstrap, arena model, placeholder champion, camera, input mapper, fixed
   step loop with interpolation, debug overlay. CI runs asset validation.
3. **First blood.** Sim: effects toolkit, projectiles, areas, line of sight,
   statuses, health and death, energy, cooldowns and windups, match flow with
   sudden death. Client: HUD, projectile and area rendering, events to
   effects, two complete champions.
4. **Bots 2v2, the first playable.** Bots: grid navigation, steering, utility
   intents, aim leading, difficulty tiers, bot-versus-bot integration tests.
   Content: champions three and four, bot profiles for all four. Client:
   champion select, match setup (team size, bot difficulty), result screen,
   first pass effects and sound.
5. **Feel and breadth.** Blender rigs and animation clips, animation state
   machine in the client, hit feedback, menus and keybinding, settings
   persistence through the platform interface, a second arena, 3v3, roster to
   six, a balance pass with a recorded bot-versus-bot win-rate report.
6. **Online.** `protocol` package, match server, WebSocket transport, lobby
   and ready flow, snapshot interpolation, client prediction and
   reconciliation, reconnect, server-side bots filling empty slots, Docker
   image and a first deployment.
7. **Ladder.** Accounts and sessions, profiles, matchmaking service, casual
   and ranked queues, Glicko-2 ratings, seasons, leaderboard, match history.
8. **Steam.** `desktop` package with Electron, Steamworks platform
   implementation (identity, achievements, rich presence), builds for macOS,
   Windows and Linux, gamepad support, store-ready packaging.
9. **Live.** Replays from input streams, spectating, telemetry, balance
   tooling, more champions and arenas, additional modes such as 1v1.

## 12. Risks and mitigations

- Retrofitting netcode: avoided by the server-authoritative sim from day one.
- Browser responsiveness: the local sim runs in-process at zero latency, the
  renderer interpolates, and the HUD is cheap DOM.
- Bots that are not fun: utility AI with projectile prediction, difficulty
  tiers, and a bot-only test loop from milestone 4 onward.
- Roster creep: four champions until the first playable, six until online.
- Placeholder art fatigue: accepted. Script-first assets can be refined
  without changing the pipeline, and a hand-made art pass is allowed later.
- Floating-point drift between client and server: irrelevant while the server
  is authoritative; prediction errors are corrected by snapshots.

## 13. Non-goals (whole project, for now)

Mobile and console builds, a map editor, mod support, cosmetics or
monetization, voice chat, and any mode beyond 2v2, 3v3 and later 1v1.
